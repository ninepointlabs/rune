Done (in native/, the current app)

  • Document I/O: .odt native read/write; .docx/.doc via an async soffice batch-conversion bridge — verified against real-world files, not just our own writer's output
  • Full text editing: keyboard, mouse, clipboard — native TextEdit behavior, not custom-built
  • File Open / Save / Save As / New with native file dialogs, and a Save / Discard / Cancel prompt before unsaved changes are lost (New, Open, or closing the window)
  • Undo/redo (toolbar, Ctrl+Z / Ctrl+Shift+Z) — every formatting, list and table operation is exactly one step, tested per operation; typing undoes a word at a time, not a paragraph at a time
  • Formatting: Bold/Italic/Underline, paragraph styles with named/inherited style resolution on import (styles.xml parent-style-name chains), bullet/numbered lists with promote/demote nesting, alignment, font family/size, text color
  • Tables: insert, insert/delete row, insert/delete column, Tab/Shift+Tab cell navigation
  • Pages: page-sized sheets at the document's paper size and margins (Letter or A4 by locale), “Page N of M” in the status bar, and File → Page setup… for paper, orientation and margins — saved in .odt and .docx, checked against LibreOffice's own .docx conversion
  • Headers and footers: double-click a margin to edit in place, formatted with the toolbar, with page number and page count fields (each page draws its own) and Ctrl+K → Page numbers — saved with real PAGE/NUMPAGES fields, so Word and LibreOffice show them in the same place
  • Command palette (Ctrl+K): every command, searchable, with its shortcut
  • Author tooling, one file per book: headings from the toolbar (Body, H1–H3; Ctrl+Alt+0–3); an outline sidebar listing chapters and scenes with word counts, click to go, drag to move a whole section (one undo step); story notes for characters, places and research, saved in the file
  • Citations: CSL-JSON sources (a form, or BibTeX import), Insert citation (Ctrl+Shift+C), APA 7, MLA 9, Chicago author-date and IEEE, and a bibliography that follows every change. Saved as text between hidden bookmarks, so Word and LibreOffice show the citations and Rune finds them again, through .docx too
  • Agents and story data: the AI reads the notes and sources, cites with Pandoc's [@key], and adds sources and notes in data blocks; sources it adds are flagged until reviewed, and their DOI or URL is checked
  • Rune's own ODF writer: headings as headings (Word's Heading 1–6 after conversion), links, lists that keep their numbering across interruptions, tables with merged cells, nested tables, widths and borders — it replaced Qt's writer, which dropped heading levels and nested tables and broke a table right after a list (an A/B check against Qt's writer still shows it)
  • .docx conversion runs off the main thread (QtConcurrent) — empirically proven not to block the UI, not just an API shape change

AI integration — the actual differentiator

Everything else on this page is table stakes. This is the reason the project exists. Sign-in, streaming and document editing are built.

  • Sign in with ChatGPT — ChatGPT Plus/Pro users use their existing plan (OpenAI's open-source plan-usage program), with verified ID tokens, rotating refresh and revoke on sign-out
  • OpenRouter sign-in (OAuth PKCE) — Claude, GPT and Grok models on the user's OpenRouter credits
  • Streaming responses, model picker, secrets in the desktop keyring, and an AI side panel (toolbar AI, or Ctrl+Shift+E to start an edit). No Rune server or account: requests go straight from your machine to your provider
  • Edit the document: corrections applied in place (spelling, grammar, wording, keeping formatting), or new text replacing the selection or written at the cursor, streamed in live and applied as one undo step; Ask mode answers questions with the document as context
  • Formatting changes by instruction ("bold the names"), and an inline prompt at the selection
  • Optional API keys for Anthropic or xAI directly. Direct Claude/Grok sign-in isn't possible: Anthropic's terms prohibit third-party Claude.ai login, and xAI has no third-party OAuth program

Architecture notes for contributors

The current app (native/) is a single process built on QTextDocument — no sockets, no protocol, no IPC. DocumentController is the QML-facing editing API (including streamed AI edits as one undo step); OdfReader/DocxBridge are plain C++ handling ODF import and the .docx conversion bridge. native/ai/ is the AI layer: AiManager (QML-facing), ChatGptProvider/OpenRouterProvider, the OAuth loopback listener, JWT verification (OpenSSL), the SSE parser and keyring storage (libsecret).
An earlier two-process LibreOfficeKit design (legacy-lok/) is kept for reference, not actively developed. See legacy-lok/README.md and the main README's architecture section for why it was replaced.
Run native/build/rune --auto-test (headless, QT_QPA_PLATFORM=offscreen) after any change — 487 checks covering formatting, tables, lists, undo/redo, pages and Page setup, headers and footers, the command palette, the file Open/Save flow, the File menu and autosave, save/load round-trips verified via real soffice conversion, and both AI sign-in flows plus every AI edit path against local mock servers. A test run never touches the real keyring, settings or browser.
Verify Qt/ODF API behavior against real files and the running app before relying on it. Silent failures this project has found that way: Qt's ODF writer mangling list-then-table structure (xmllint plus a direct A/B soffice test) and dropping heading levels; QTextDocument::clear() resetting the modified flag and undo history without emitting the signals that say so; Qt 6.11's ahead-of-time compiled QML resolving MessageDialog's button enums to undefined; and, in the retired LOK engine, .uno: commands that returned ok while doing nothing. Don't assume an API's documented behavior is what actually happens — test it.
