Done (in native/, the current app)

  • Document I/O: .odt native read/write; .docx/.doc via an async soffice batch-conversion bridge — verified against real-world files, not just our own writer's output
  • Full text editing: keyboard, mouse, clipboard — native TextEdit behavior, not custom-built
  • Formatting: Bold/Italic/Underline, paragraph styles with named/inherited style resolution on import (styles.xml parent-style-name chains), bullet/numbered lists with promote/demote nesting, alignment, font family/size, text color
  • Tables: insert, insert/delete row, insert/delete column, Tab/Shift+Tab cell navigation
  • A save-time sanitizer working around a real Qt ODF-writer bug (see below) — verified with a direct A/B test, not an assumption
  • .docx conversion runs off the main thread (QtConcurrent) — empirically proven not to block the UI, not just an API shape change

Architecture notes for contributors

The current app (native/) is a single process built on QTextDocument — no sockets, no protocol, no IPC. DocumentController is the QML-facing editing API; OdfReader/DocxBridge are plain C++ (not QML-exposed) handling ODF import and the .docx conversion bridge respectively.
An earlier two-process LibreOfficeKit design (legacy-lok/) is kept for reference, not actively developed. See legacy-lok/README.md and the main README's architecture section for why it was replaced.
Run native/build/rune --auto-test (headless, QT_QPA_PLATFORM=offscreen) after any change — 158 checks covering formatting, tables, lists, and save/load round-trips verified via real soffice conversion, not just a successful-looking return value.
Verify Qt/ODF API behavior against real files before relying on it. This project has twice found real, silent-failure bugs this way — Qt's own ODF writer mangling list-then-table structure (confirmed with xmllint plus a direct A/B soffice conversion test), and earlier, the old LOK engine's .uno: commands that returned ok while silently doing nothing (confirmed by diffing rendered tiles). Don't assume an API's documented behavior is what actually happens on disk — test it.
